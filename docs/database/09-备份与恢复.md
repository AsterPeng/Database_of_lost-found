# 09 备份与恢复

## 1. 目标

验证在数据库课程化改造后：

- 能对展示库做一致性备份；
- 能把备份恢复到独立临时库；
- 恢复后的数据行数、校验和、视图、物化视图、触发器、RLS 策略与源库一致；
- 明确数据库备份与文件存储、加密密钥、集群级角色之间的关系；
- 给出生产环境 PITR（时间点恢复）的设计说明。

## 2. 备份脚本

脚本：[scripts/db/backup-restore.ps1](../../scripts/db/backup-restore.ps1)

用法：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/db/backup-restore.ps1
```

默认行为：

1. 从项目根目录 `.env` 读取 `DATABASE_URL`（当前指向 `clfp_enhanced`）；
2. 用 `pg_dump --format=custom --no-owner --no-privileges` 备份到 `D:\ClaudeCodeProjects\clfp-backups\clfp_enhanced_<时间戳>.dump`；
3. 重建临时库 `clfp_restore_check`；
4. 用 `pg_restore --no-owner --no-privileges --exit-on-error` 恢复；
5. 对比源库与恢复库的行数、校验和、对象数量；
6. 校验通过后删除临时库。

脚本会拒绝把 `clfp_original` 作为备份源，避免误操作原项目冻结库。输出中的连接串已对密码做脱敏。

## 4. 数据库备份之外的资产

### 4.1 图片文件

`post_images.path` 指向 `storage/uploads/`，图片二进制不在数据库里。恢复时必须同时备份/恢复该目录：

```text
storage/uploads/2026/10/0d82666c7f248e2ef9f6400093bdb4d4.jpg
```

数据库恢复后如果图片文件缺失，页面图片接口会返回 404，但数据与文字内容不受影响。

### 4.2 加密密钥

`ENCRYPTION_KEY` 在 `.env` 中，**不进入数据库备份**。手机号、认领联系方式的密文只有配合该密钥才能解密；更换密钥会导致旧密文不可读。密钥必须单独备份，并且不能和备份文件放在同一位置。

### 4.3 集群级角色

`clfp_owner`、`clfp_app`、`clfp_stats`、`clfp_readonly`、`clfp_rls_demo` 是**集群级对象**，不属于单个数据库。`pg_dump --no-privileges` 不导出 GRANT；RLS 策略虽然会随表结构导出，但策略引用的角色必须在新集群中先存在。

新集群恢复顺序：

1. 创建角色：执行 `db/sql/06_roles_rls.sql` 中的 `CREATE ROLE` 部分（或完整脚本）；
2. 恢复数据库备份；
3. 重新执行 `06_roles_rls.sql` 的授权与 RLS 部分，确保 GRANT 与策略完整；
4. 恢复 `storage/uploads`；
5. 设置相同的 `ENCRYPTION_KEY` 与 `DATABASE_URL`。

## 5. 恢复命令（手工版）

```bash
# 1. 备份
pg_dump --format=custom --no-owner --no-privileges \
  --file=clfp_enhanced.dump "postgresql://.../clfp_enhanced"

# 2. 新建临时库
psql "postgresql://.../postgres" -c "DROP DATABASE IF EXISTS clfp_restore_check WITH (FORCE);"
psql "postgresql://.../postgres" -c "CREATE DATABASE clfp_restore_check;"

# 3. 恢复
pg_restore --no-owner --no-privileges --exit-on-error \
  --dbname="postgresql://.../clfp_restore_check" clfp_enhanced.dump

# 4. 校验
psql "postgresql://.../clfp_restore_check" -c "SELECT count(*) FROM users;"
```

Windows 下 `pg_dump`/`pg_restore` 位于 `D:\Program Files\PostgreSQL\18\bin`，脚本已使用绝对路径。

## 6. 生产环境 PITR 设计说明

本机没有配置 WAL 归档，P7 只做逻辑备份。生产环境建议：

### 6.1 开启 WAL 归档

```conf
wal_level = replica
archive_mode = on
archive_command = 'copy "%p" "D:\\pg_wal_archive\\%f"'
```

### 6.2 基础备份

```bash
pg_basebackup -D base -Ft -z -P -h 127.0.0.1 -U postgres
```

### 6.3 时间点恢复

恢复时在 `postgresql.conf` 或 `recovery.conf` 中配置：

```conf
restore_command = 'copy "D:\\pg_wal_archive\\%f" "%p"'
recovery_target_time = '2026-11-02 15:00:00+08'
```

启动后 PostgreSQL 会重放 WAL 到目标时间点。恢复完成后执行 `pg_wal_replay_resume()` 或确认自动结束。

### 6.4 备份策略

| 类型 | 频率 | 保留 |
| --- | --- | --- |
| 逻辑备份 `pg_dump -Fc` | 每日 | 7~30 天 |
| 基础备份 + WAL 归档 | 每周基础备份，WAL 持续归档 | 按 RPO/RTO 要求 |
| `storage/uploads` | 与数据库同步 | 与数据库一致 |
| `ENCRYPTION_KEY` | 变更时立即备份 | 永久，单独保管 |

## 7. 安全注意事项

- 备份文件包含手机号/认领联系方式的密文，虽然不能直接解密，但仍应按敏感数据保护；
- 不要把备份文件提交到 Git（`.gitignore` 已忽略 `/backups/`，本项目备份放在仓库外的 `clfp-backups`）；
- 脚本输出中的连接串已脱敏，不打印密码；
- 恢复验证使用临时库，校验通过后立即删除，避免长期保留测试副本。

## 8. 结论

- 逻辑备份与恢复流程可用，行数、校验和与数据库对象完全一致；
- 图片文件、加密密钥、集群级角色必须作为独立的恢复资产管理；
- 生产环境应补充 WAL 归档与 PITR，逻辑备份不能替代时间点恢复；
- P7 验证未修改 `clfp_enhanced` 的业务数据，也未操作 `clfp_original`。

# 02 逻辑设计

## 1. 表示约定

关系模式采用以下记号：

- 下划线或 `PK` 标注主键，`FK` 标注外键，`UQ` 标注唯一约束；
- `X → Y` 表示函数依赖“X 决定 Y”；
- 关系模式中的属性名使用数据库列名，实体名使用表名；
- “全部非键属性”指该关系中除候选键以外的所有属性。

当前数据库共 17 张业务表、9 个枚举类型、23 个外键约束。完整 DDL 见 `db/sql/00_schema.sql`。

## 3. 候选键与函数依赖

### 3.1 用户与会话

- `users`：`id → 全部非键属性`；`email → 全部非键属性`。`email` 与 `id` 都是候选键。
- `student_no` 在业务上可能被期望唯一，但数据库**没有唯一约束**，因此目前不能把它当作候选键；若业务要求学号唯一，应补 `UNIQUE(student_no)`，并处理 NULL 值（PostgreSQL 唯一索引允许多个 NULL）。
- `sessions`：`id → 全部`；`token_hash → 全部`。`user_id` 只能决定“该用户有哪些会话”，不能决定单条会话，因此不是候选键。

### 3.2 帖子与内容

- `categories`：`id → 全部`；`name → 全部`。
- `posts`：`id → 全部`。业务上没有天然的唯一键；“同一作者同一天发布同标题”可能重复，不能作为候选键。
- `post_images`：`id → 全部`。`(post_id, sort_order)` 在业务上看似唯一，但当前没有唯一约束，因此不是候选键；P2 建议补 `UNIQUE(post_id, sort_order)`。
- `post_embeddings`：`post_id → 全部`。`post_id` 既是主键，也是指向帖子的外键。
- `embedding_tasks`：`id → 全部`。同一帖子可以有多个任务，`post_id` 不是候选键。

### 3.3 匹配、认领与交接

- `matches`：`id → 全部`；`(lost_post_id, found_post_id) → 全部`。给定一对失物/拾物，最多一条匹配记录。
- `claims`：`id → 全部`；`(post_id, claimant_id) → 全部`。`match_id` 只表示来源，不能决定认领状态；`status` 由审核动作决定。
- `handovers`：`id → 全部`；`claim_id → 全部`（`claim_id` 有唯一约束，因此是候选键）。
- `contact_grants`：`id → 全部`；`(claim_id, grantor_id) → 全部`。`grantee_id` 理论上可由“认领双方中除 grantor 外的另一方”推导，但当前仍以列存储，属于受控冗余。

### 3.4 通知与治理

- `notifications`：`id → 全部`。`user_id` 不是候选键。
- `notification_preferences`：`user_id → 全部`。
- `audit_logs`：`id → 全部`。日志是追加写，业务上没有自然键；允许同一操作产生多条日志。
- `reports`：`id → 全部`；`(reporter_id, target_type, target_id) → 全部`。
- `announcements`：`id → 全部`。标题与发布时间不保证唯一。
- `app_configs`：`key → value, updated_at`。

## 4. 范式分析

### 4.1 第一范式（1NF）

1NF 要求每个属性都是不可再分的原子值，且不允许重复组。逐表检查：

- 所有业务表的普通列（文本、数字、布尔、时间、枚举）都是原子值；
- `matches.detail`、`audit_logs.detail`、`app_configs.value` 是 JSONB，内部有结构，但数据库把它们当作一个整体值读写，不按内部键查询或连接；
- `post_embeddings.vector` 是 `double precision[]` 数组，按“一个向量值”整体读写；
- `posts` 的配图没有内嵌在帖子行里，而是拆到 `post_images`，避免了重复组。

严格按经典关系理论，JSON 文档与数组都不满足“每个分量原子”的定义。本设计将它们视为**现代 PostgreSQL 的复合值/半结构化值**，理由是：它们不需要被其他关系外键引用，也不会按内部字段做连接；拆表会带来大量稀疏行或数百行的向量维度表，收益低。这一取舍在 7.4 节与 02-逻辑设计的反规范化部分说明。

**结论**：核心关系满足工程意义上的 1NF；JSON 与数组属性是有意的受控例外。

### 4.2 第二范式（2NF）

2NF 要求非主属性完全依赖于候选键，而不是只依赖候选键的一部分。可能出问题的只有复合候选键关系：

| 关系 | 复合候选键 | 检查 |
| --- | --- | --- |
| `matches` | `(lost_post_id, found_post_id)` | `score`、`detail`、`feedback`、`created_at` 依赖整对匹配，不单独依赖某一端；通过 |
| `claims` | `(post_id, claimant_id)` | `message`、`proof`、`status`、`escalate_at` 依赖“谁对哪条帖子申请”，通过 |
| `contact_grants` | `(claim_id, grantor_id)` | `grantee_id`、`revoked_at` 依赖“哪条认领的哪一方授权”，通过 |
| `reports` | `(reporter_id, target_type, target_id)` | `reason`、`status` 依赖“谁举报了哪个对象”，通过 |

其余关系以单列主键为主（`post_embeddings.post_id`、`notification_preferences.user_id`、`app_configs.key`），不存在部分依赖。

**结论**：满足 2NF。

### 4.3 第三范式（3NF）

3NF 要求非主属性不传递依赖于候选键。逐项检查容易出问题的字段：

- `posts.category_id` 只存类别 ID，类别名称在 `categories` 表中，不存在“帖子 → 类别 ID → 类别名称”的传递依赖；
- `users.department` 只存院系名称，没有院系编码、负责人等属性，当前不存在“用户 → 院系 → 其他属性”的传递依赖；
- `claims.reviewer_role` 记录审核时的角色快照（`OWNER`/`ADMIN`）。它不依赖 `reviewed_by_id` 当前的角色，因为用户角色可能变化；这是历史快照，不是传递依赖；
- `posts.resolved_at` 是状态变更事件的时间戳，不是由 `status` 推导出的普通属性；
- `contact_grants.grantee_id` 依赖复合键 `(claim_id, grantor_id)`，不是传递依赖；但它与认领双方存在冗余，见 5.2；
- `matches.detail` 中的分数明细是匹配生成时的快照，`score` 是其汇总值；两者存在业务上的冗余，但 `detail` 用于解释与回溯，保留快照是有意的。

**结论**：核心关系满足 3NF。

### 4.4 BCNF

BCNF 要求每个非平凡函数依赖的决定因素都是候选键。

- `users`：决定因素 `id`、`email` 都是候选键；通过。
- `sessions`：`id`、`token_hash` 都是候选键；通过。
- `categories`：`id`、`name` 都是候选键；通过。
- `posts`、`post_images`、`embedding_tasks`、`notifications`、`audit_logs`、`announcements`：只有主键作为决定因素；通过。
- `post_embeddings`、`notification_preferences`、`app_configs`：单列主键；通过。
- `matches`、`claims`、`contact_grants`、`reports`、`handovers`：复合候选键与主键都已识别，非键属性完全依赖于候选键；通过。
- 若未来把 `student_no` 设为唯一，则 `student_no` 成为候选键，仍是 BCNF；若只把 `department` 当字符串而不建院系表，也不产生新的决定因素。

**结论**：在忽略 JSON/数组内部结构的前提下，关系模式满足 BCNF。

## 5. 反规范化与受控冗余

### 5.1 JSONB 快照

`matches.detail`、`audit_logs.detail`、`app_configs.value` 使用 JSONB：

- `matches.detail`：保存生成匹配时的各维度分数与推荐理由。若拆成 `match_score_dimensions(match_id, dimension, value)`，可以获得更强的可查询性，但每次展示匹配都要多一次连接，且维度集合会随模型调整而变化；
- `audit_logs.detail`：不同 `action` 的上下文不同（下架原因、配置前后值、认领决定等），用 JSONB 避免为每种动作建子表；
- `app_configs.value`：配置项本身是键值对，结构由应用层校验。

**风险**：JSONB 内部字段没有数据库级类型约束，依赖应用层 zod 校验；P2 可为关键键增加 `CHECK (jsonb_typeof(value) = 'object')` 等轻量约束。

### 5.2 `contact_grants.grantee_id` 的冗余

`grantee_id` 可以由 `claims` 与 `posts` 推导：认领双方是 `claims.claimant_id` 与 `posts.author_id`，授权方是 `grantor_id`，被授权方就是另一方。当前把它显式存下来：

- 优点：查询“谁被授权看我的联系方式”时不需要三表连接；
- 风险：如果认领双方或授权方被错误写入，可能出现 `grantee_id` 与推导值不一致；
- 控制：应用层在写入时统一计算；P2 可加触发器校验 `grantee_id` 必须是该认领的另一方。

这是典型的“为了读取性能保留的受控冗余”，在 3NF 分析中仍可接受，因为 `grantee_id` 完全依赖于候选键，而不是依赖于另一个非主属性。

### 5.3 帖子可见性字段

`deleted_at`、`taken_down_at`、`archived_at` 三个字段都可以由各自的管理动作推导，但它们表达不同业务语义，合并会导致状态组合丢失。保留三个时间戳是“事件溯源式”的设计，不属于冗余。

## 6. 完整性约束设计

### 6.1 实体完整性

所有 17 张业务表都有主键，且主键列 `NOT NULL`。`_prisma_migrations` 是 Prisma 内部表，不参与业务。

### 6.2 参照完整性

当前共有 23 个外键约束，删除策略分布如下：

| 删除策略 | 数量 | 典型关系 |
| --- | --- | --- |
| `CASCADE` | 15 | 用户 → 会话/帖子/认领/通知；帖子 → 配图/向量/任务/匹配/认领；认领 → 交接/授权 |
| `SET NULL` | 6 | 审核人、下架人、反馈人、举报处理人、公告发布人、审计操作人 |
| `RESTRICT` | 1 | 类别 → 帖子：有帖子的类别不允许物理删除 |
| 无外键 | 2 组 | `claims.match_id`、`handovers.proposed_by_id/completed_by_id`、多态 `target_id` |

P2 计划补的外键：

```sql
ALTER TABLE claims
  ADD CONSTRAINT claims_match_id_fkey
  FOREIGN KEY (match_id) REFERENCES matches(id) ON DELETE SET NULL;

ALTER TABLE handovers
  ADD CONSTRAINT handovers_proposed_by_id_fkey
  FOREIGN KEY (proposed_by_id) REFERENCES users(id) ON DELETE SET NULL,
  ADD CONSTRAINT handovers_completed_by_id_fkey
  FOREIGN KEY (completed_by_id) REFERENCES users(id) ON DELETE SET NULL;
```

补之前需要先做数据校验：确认现有 `claims.match_id` 都能在 `matches` 中找到，`handovers` 的两个用户 ID 都能在 `users` 中找到，否则迁移会失败。

### 6.3 用户自定义完整性

当前已有的用户自定义约束主要是枚举、唯一索引和默认值，**没有 CHECK 约束**。P2 计划补充：

| 约束名 | 表 | 规则 | 目的 |
| --- | --- | --- | --- |
| `matches_score_check` | `matches` | `score >= 0 AND score <= 1` | 置信度必须在 0~1 |
| `matches_pair_check` | `matches` | `lost_post_id <> found_post_id` | 禁止自匹配 |
| `notification_preferences_quiet_check` | `notification_preferences` | `quiet_start BETWEEN 0 AND 23 AND quiet_end BETWEEN 0 AND 23` | 免打扰小时合法 |
| `announcements_expiry_check` | `announcements` | `expires_at IS NULL OR expires_at > published_at` | 过期时间晚于发布时间 |
| `post_images_size_check` | `post_images` | `size > 0` | 图片大小为正 |
| `post_embeddings_dim_check` | `post_embeddings` | `dim > 0 AND dim = array_length(vector, 1)` | 向量维度与声明一致 |
| `reports_target_type_check` | `reports` | `target_type IN ('POST')`（当前仅支持帖子，后续扩展） | 限制多态类型 |
| `audit_logs_target_type_check` | `audit_logs` | `target_type IN ('POST','USER','CLAIM','CATEGORY','CONFIG')` | 限制多态类型 |
| `claims_reviewer_role_check` | `claims` | `reviewer_role IS NULL OR reviewer_role IN ('OWNER','ADMIN')` | 限制审核人角色 |
| `post_images_sort_unique` | `post_images` | `UNIQUE(post_id, sort_order)` | 配图顺序唯一 |
| `claims_one_accepted_per_post` | `claims` | 部分唯一索引 `ON claims(post_id) WHERE status = 'ACCEPTED'` | 一条帖子最多一条通过 |

> 注意：部分唯一索引与现有“同一用户对同一帖子可复用被拒记录重新申请”的逻辑兼容；它只限制同一帖子最多一条 `ACCEPTED`，不限制历史 `REJECTED`/`CANCELLED` 记录。

### 6.4 触发器维护的完整性

以下规则无法用简单 CHECK 表达，P2 用触发器实现：

- `trg_post_status_transition`：只允许 `OPEN → RESOLVED`、`OPEN → CLOSED`，禁止从 `RESOLVED`/`CLOSED` 回到 `OPEN`；
- `trg_match_integrity`：匹配的 `lost_post_id` 必须指向 `LOST` 帖子，`found_post_id` 必须指向 `FOUND` 帖子，且两位作者不同；
- `trg_claim_audit`：认领审核动作写入 `audit_logs`；
- 可选 `trg_claim_result_notification`：认领通过/拒绝后生成通知（当前仍由应用层生成，P2 评估后再决定是否下沉）。

## 7. 规范化结论与待改进

**结论**：

- 17 张业务表均满足 2NF；
- 核心关系满足 3NF 与 BCNF；
- JSONB 与向量数组是有意的半结构化/复合值设计；
- 当前主要问题不是范式，而是**约束不够强**：缺少 CHECK、部分唯一索引、部分外键与触发器，导致完整性过度依赖应用层。

**P2 优先补齐**：

1. `claims.match_id`、`handovers.proposed_by_id/completed_by_id` 外键；
2. `matches` 分数范围、自匹配检查；
3. 一条帖子最多一条 `ACCEPTED` 认领的部分唯一索引；
4. 免打扰小时、公告过期、配图大小等 CHECK；
5. 帖子状态机、匹配一致性触发器；
6. `post_images(post_id, sort_order)` 唯一约束。

这些改动会在 `05-数据库对象设计.md` 中给出完整 SQL 与回滚方案。

# 07 权限与安全设计

## 1. 目标

本阶段把数据库从“应用使用单一高权限账号”改造成**按职责分权**的结构，并用行级安全（RLS）演示“用户只能看到自己的数据”。目标不是替换应用现有的权限判断，而是在数据库层再加一道防线，体现数据库课程中的自主存取控制、最小权限原则与行级安全。

## 2. 角色定义

| 角色 | 登录 | 职责 | 关键权限 |
| --- | --- | --- | --- |
| `clfp_owner` | 否 | 运维/DDL 权限组 | 所有业务表的 DML、序列、函数执行、public schema 的 CREATE |
| `clfp_app` | 否 | 应用运行角色 | 业务表 SELECT/INSERT/UPDATE/DELETE，函数执行；**无 DDL** |
| `clfp_stats` | 否 | 统计报表角色 | 统计视图、物化视图、`fn_stats`；基础表只授予统计所需列 |
| `clfp_readonly` | 否 | 公开只读角色 | `v_public_posts`、`v_match_overview` 与用户公开列 |
| `clfp_rls_demo` | 否 | RLS 演示角色 | 只读通知、认领、联系方式授权、帖子的必要列；受 RLS 策略约束 |

实际开发账号 `clfp` 是对象属主，并被授予上述角色，便于通过 `SET ROLE` 做演示。生产环境应创建独立登录角色并授予 `clfp_app`，而不是让应用使用属主账号。

## 3. 授权矩阵

| 对象 | `clfp_owner` | `clfp_app` | `clfp_stats` | `clfp_readonly` | `clfp_rls_demo` |
| --- | --- | --- | --- | --- | --- |
| 业务表（users/posts/claims 等） | CRUD | CRUD | 仅统计所需列 | 无 | 无 |
| `v_public_posts` | ✓ | ✓ | ✓ | ✓ | 无 |
| `v_match_overview` | ✓ | ✓ | ✓ | ✓ | 无 |
| `v_admin_dashboard` | ✓ | ✓ | ✓ | 无 | 无 |
| `v_pending_claims` | ✓ | ✓ | ✓ | 无 | 无 |
| `v_unread_notifications` | ✓ | ✓ | ✓ | 无 | 无 |
| `mv_stats_department` / `mv_stats_category` | ✓ | ✓ | ✓ | 无 | 无 |
| `fn_stats` | ✓ | ✓ | ✓ | 无 | 无 |
| `fn_review_claim` / `fn_escalate_overdue_claims` / `fn_complete_handover` | ✓ | ✓ | 无 | 无 | 无 |
| `fn_refresh_stats_mv` | ✓ | 撤销 | 无 | 无 | 无 |
| `_prisma_migrations` | 撤销 | 撤销 | 撤销 | 撤销 | 撤销 |
| 公开用户列（id、nickname、department） | ✓ | ✓ | 统计所需列 | ✓ | 无 |
| `phone_encrypted` / `contact_encrypted` / `password_hash` | 属主可访问 | 属主可访问 | **无** | **无** | **无** |

说明：

- `clfp_app` 对业务表有完整 DML，因为应用需要写入加密字段；生产环境应通过应用层权限与审计控制，而不是依赖数据库列权限。
- `clfp_stats` 通过列级授权执行 `fn_stats`，只能读取聚合所需列，不能读取手机号密文、密码哈希或认领联系方式密文。
- `clfp_readonly` 只适合公开信息浏览；它没有任何认领、通知、审计表权限。
- RLS 演示角色只授予策略判断所需的列，避免“有 RLS 但能读敏感列”的假安全。

## 4. 行级安全策略

对 `notifications`、`claims`、`contact_grants` 启用 RLS：

```sql
ALTER TABLE notifications ENABLE ROW LEVEL SECURITY;
ALTER TABLE claims ENABLE ROW LEVEL SECURITY;
ALTER TABLE contact_grants ENABLE ROW LEVEL SECURITY;
```

策略使用事务级配置变量 `app.current_user_id`：

```sql
-- 用户只看自己的通知
CREATE POLICY notifications_self_select ON notifications
  FOR SELECT TO clfp_rls_demo
  USING (user_id = current_setting('app.current_user_id', true));

-- 认领对申请人或帖子作者可见
CREATE POLICY claims_party_select ON claims
  FOR SELECT TO clfp_rls_demo
  USING (
    claimant_id = current_setting('app.current_user_id', true)
    OR EXISTS (
      SELECT 1 FROM posts p
      WHERE p.id = claims.post_id
        AND p.author_id = current_setting('app.current_user_id', true)
    )
  );

-- 联系方式授权对授权方或被授权方可见
CREATE POLICY contact_grants_party_select ON contact_grants
  FOR SELECT TO clfp_rls_demo
  USING (
    grantor_id = current_setting('app.current_user_id', true)
    OR grantee_id = current_setting('app.current_user_id', true)
  );
```

演示时在同一事务内执行：

```sql
SET LOCAL ROLE clfp_rls_demo;
SELECT set_config('app.current_user_id', '用户 ID', true);
SELECT id FROM notifications;
```

事务结束后角色与配置变量自动恢复，避免连接池串号。

## 5. 为什么表属主仍是 clfp，且没有 FORCE RLS

- Prisma 迁移需要对象属主权限；如果把所有表改归 `clfp_owner`，现有 `npx prisma migrate` 会因属主不匹配而需要额外 `SET ROLE`，容易破坏部署流程。
- PostgreSQL 默认允许表属主绕过 RLS。`clfp` 作为属主继续服务现有应用，RLS 不会影响 3001 展示环境。
- 没有使用 `FORCE ROW LEVEL SECURITY`，因为那会让属主也受策略约束，而应用尚未按请求设置 `app.current_user_id`。生产环境若要启用强制 RLS，应在连接层为每个请求执行 `SET LOCAL app.current_user_id`，并移除 `*_app_all` 策略。
- `clfp_app` 与 `clfp_owner` 配置了 `USING (true)` 策略，避免 RLS 把正常应用 DML 拦掉；`clfp_rls_demo` 才是受限制的演示角色。

## 6. 执行步骤

创建角色需要 CREATEROLE 或超级用户权限；本项目开发账号 `clfp` 默认没有 CREATEROLE。推荐临时授权：

```sql
-- 由 postgres 超级用户执行一次
ALTER ROLE clfp CREATEROLE;
```

然后在**增强库与测试库**分别执行（不要对原项目冻结库执行）：

```bash
# 增强库
psql "$CLFP_ENHANCED_URL" -v ON_ERROR_STOP=1 -f db/sql/06_roles_rls.sql

# 测试库
psql "$CLFP_TEST_URL" -v ON_ERROR_STOP=1 -f db/sql/06_roles_rls.sql
```

完成后收回建角色权限：

```sql
-- 由 postgres 超级用户执行
ALTER ROLE clfp NOCREATEROLE;
```

> 角色是集群级对象，脚本对多个数据库重复执行时会跳过已存在的角色，只重新应用授权与 RLS 策略。

## 8. 生产环境建议

- 为应用创建独立登录角色 `clfp_login`，授予 `clfp_app`，连接串不再使用 `clfp` 属主账号；
- 每个请求在事务开始时 `SET LOCAL app.current_user_id = ...`，并移除 `*_app_all` 策略，让应用也受 RLS 约束；
- 密码、手机号、认领联系方式继续使用应用层加密；数据库列权限只作为第二道防线；
- 生产环境启用 `pg_audit` 或至少保留 `audit_logs` 的只增权限；
- 定期审查角色成员与授权，避免 `clfp_owner` 被应用账号继承。

### 9.2 `fn_stats` 的权限缺陷与修复

**现象**：`clfp_stats` 按设计只有列级授权，调用 `fn_stats` 时报 `42501 对表 users 权限不够`。

**原因**：`fn_stats` 是 `SECURITY INVOKER` 函数，内部 CTE 使用了 `SELECT u.*` 与 `p.*`。PostgreSQL 要求 `SELECT *` 具备整表 `SELECT` 权限，而 `clfp_stats` 只有统计所需列的单列授权，因此函数以调用者权限执行时被拒绝。

**修复**：在 `db/sql/03_functions.sql` 中把 `user_scope`、`new_user_scope`、`post_scope` 改为显式列清单：

- `user_scope`：只取 `department`；
- `new_user_scope`：只取 `id`；
- `post_scope`：显式列出 `id`、`author_id`、`category_id`、`status`、`taken_down_at`、`created_at`、`deleted_at`。

统计口径未改变，并已用 `CREATE OR REPLACE` 应用到 `clfp_enhanced` 与 `clfp_test`。

**复核**：在两个库分别执行

```sql
BEGIN;
SET LOCAL ROLE clfp_stats;
SELECT (fn_stats(NULL::timestamptz, NULL::timestamptz, NULL::text)->'totals') AS totals;
RESET ROLE;
COMMIT;
```

均成功返回，没有 42501：

- `clfp_enhanced`：`{"posts":1,"users":2,"claims":0,"matches":0,"newUsers":2,"resolved":0,"takenDown":0}`
- `clfp_test`：`{"posts":22,"users":11,"claims":7,"matches":25,"newUsers":11,"resolved":2,"takenDown":1}`

这个缺陷说明：列级授权与 `SECURITY INVOKER` 函数必须配合显式列清单；`SELECT *` 会无意中要求整表权限，抵消最小权限设计。

> 注意：为避免已应用迁移的 checksum 冲突，`prisma/migrations/20261102092000_db_course_functions/migration.sql` 中的旧定义没有直接修改；修正位于 `db/sql/03_functions.sql`，并已 `CREATE OR REPLACE` 到 `clfp_enhanced` 与 `clfp_test`。若以后从零重建数据库，需要在 `prisma migrate deploy` 后重新执行 `03_functions.sql` 中的 `fn_stats` 定义，或补一条只包含 `CREATE OR REPLACE FUNCTION fn_stats` 的修正迁移。

### 9.5 CREATEROLE 状态与重跑说明

- 验证结束后已执行 `ALTER ROLE clfp NOCREATEROLE;`，复核结果为 `clfp super=false、createrole=false`；当前只有 `postgres` 具有 CREATEROLE。
- 收回 CREATEROLE 不会删除已创建的角色，也不会撤销角色成员关系；五个角色与授权仍然有效。
- 后续如需重建角色或重新执行 `06_roles_rls.sql`，需要再次由 `postgres` 临时授权：

```sql
ALTER ROLE clfp CREATEROLE;
-- 执行 06 脚本
ALTER ROLE clfp NOCREATEROLE;
```

- 仓库根目录的 `01-临时授予CREATEROLE权限.bat` 与 `02-收回CREATEROLE权限.bat` 是双击辅助脚本：固定使用 `D:\Program Files\PostgreSQL\18\bin\psql.exe` 连接 `127.0.0.1:5432`，运行时提示输入 `postgres` 密码，脚本内**不包含明文密码**；文件保持 GBK 编码 + CRLF 换行以兼容中文 cmd。是否纳入版本库由最终提交决定。
- 本轮没有对 `clfp_original` 执行任何 P4 脚本，也没有修改 RLS 策略或授权矩阵。

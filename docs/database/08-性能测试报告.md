# 08 性能测试报告

## 1. 测试目标

在 10 万级数据下验证：

- 公开信息流、关键词搜索、认领队列、未读通知等高频查询是否能命中索引；
- P2 建立的索引哪些真正有效，哪些被已有复合索引覆盖；
- 统计函数 `fn_stats` 在 10 万级数据下的耗时，以及物化视图能否作为全量总览的替代方案；
- 为课程报告提供可复现的 `EXPLAIN (ANALYZE, BUFFERS)` 证据。

## 3. 基准结果

运行方式：

```bash
DATABASE_URL="postgresql://.../clfp_bench" npx tsx scripts/db/benchmark.ts
```

每个查询执行 3 次取中位数；索引对比会临时删除目标索引，测量后再重建。

| 查询 | 有索引 | 无索引 | 提升 |
| --- | --- | --- | --- |
| 公开信息流（LOST + 时间倒序 + LIMIT 12） | 0.02 ms | 9.91 ms | **约 431 倍** |
| 中文关键词搜索（`title ILIKE '%稀有物品%'`） | 1.40 ms | 56.15 ms | **约 40 倍** |
| 待审认领队列（PENDING + `escalate_at`） | 0.03 ms | 0.02 ms | 基本无变化 |
| 未读通知计数（单用户） | 0.04 ms | 0.03 ms | 基本无变化 |
| 统计函数 `fn_stats`（全部时间） | 3,532 ms | — | — |
| 统计函数 `fn_stats`（最近 30 天） | 1,206 ms | — | — |
| 院系物化视图（全部时间） | 0.02 ms | — | — |
| 类别物化视图（全部时间） | 0.03 ms | — | — |
| 匹配候选（`feedback=NONE` + 时间倒序） | 0.03 ms | — | — |

物化视图刷新耗时：**250 ms**。

完整执行计划见 [assets/benchmark-explain.txt](assets/benchmark-explain.txt)。

## 4. 关键执行计划

### 4.1 公开信息流

有索引时：

```text
Limit
  -> Index Scan using posts_public_feed_idx on posts
       (actual time=0.006..0.009 rows=12)
```

无索引时：

```text
Limit
  -> Sort (Sort Key: created_at DESC)
       -> Bitmap Heap Scan on posts
            -> Bitmap Index Scan on posts_type_status_idx
Execution Time: 9.489 ms
```

`posts_public_feed_idx` 是部分索引，直接按 `(type, created_at DESC)` 返回有序结果，避免了 47,000 行候选的排序。

### 4.2 中文关键词搜索

有索引时：

```text
Bitmap Index Scan on posts_title_trgm_idx
  (actual time=0.090..0.090 rows=1000)
```

无索引时：

```text
Seq Scan on posts
  (actual time=0.068..55.782 rows=945)
Execution Time: 55.912 ms
```

`pg_trgm` 的 GIN 索引把中文 `ILIKE '%关键词%'` 从全表扫描变成 945 行命中的 Bitmap Index Scan。

### 4.3 认领队列

有索引与无索引都使用：

```text
Index Scan using claims_status_escalate_at_idx on claims
```

说明 P2 新增的 `claims_pending_escalate_idx` 被已有的 `(status, escalate_at)` 复合索引完全覆盖。两者耗时都是 0.02~0.03 ms，没有可测收益。

### 4.4 未读通知

- 有部分索引：`Index Scan using notifications_unread_idx`
- 无部分索引：`Index Scan using notifications_user_id_read_at_idx`

两者都是 0.03~0.04 ms。已有的 `(user_id, read_at)` 复合索引已经足够，P2 的 `notifications_unread_idx` 在当前查询下没有可测收益。

### 4.5 统计函数与物化视图

`fn_stats` 的执行计划只显示 `Result`，函数内部 CTE 被整体执行：

```text
Result (actual time=3491.595..3492.108 rows=1)
Buffers: shared hit=28673, temp read=11991 written=9333
Execution Time: 3492.118 ms
```

最近 30 天为 1,206 ms。全量统计需要扫描并连接 users/posts/matches/claims，10 万级下达到秒级。

物化视图查询只扫描 8 行/6 行：

```text
Seq Scan on mv_stats_department (actual time=0.005..0.005 rows=8)
Execution Time: 0.015 ms
```

刷新物化视图耗时 250 ms。也就是说，**全量总览用物化视图的代价是 250 ms 刷新一次，换到 0.02 ms 查询**，远优于每次 3.5 秒的实时聚合。

## 5. 分析与结论

### 5.1 有效索引

- `posts_public_feed_idx`：公开信息流提升约 431 倍，是最有价值的索引；
- `posts_title_trgm_idx`：中文模糊搜索提升约 40 倍；
- `matches_created_at_idx`：匹配候选查询稳定在 0.03 ms；
- `users_department_idx`、`claims_created_at_idx`、`matches_created_at_idx` 为统计的时间/院系筛选提供基础。

### 5.2 冗余索引

`claims_pending_escalate_idx` 和 `notifications_unread_idx` 在当前查询下没有可测收益：

- 认领队列已有 `(status, escalate_at)` 复合索引；
- 未读通知已有 `(user_id, read_at)` 复合索引。

它们仍然更小（736 KB vs 880 KB；2,080 KB vs 3,976 KB），在更大数据量或更极端的查询下可能仍有价值。如果写放大成为问题，可以考虑删除；当前保留，作为针对性索引。

### 5.3 统计口径的取舍

- 带时间范围/院系筛选的实时报表走 `fn_stats`，30 天约 1.2 秒；
- 全部时间的总览走物化视图，查询 0.02 ms，刷新 250 ms；
- 当前应用页面统一调用 `fn_stats`，在 10 万级数据下全量统计会明显变慢。生产环境建议：
  - 全量总览直接读 `mv_stats_department` / `mv_stats_category`；
  - 带筛选的报表继续用 `fn_stats`，并考虑短时缓存或按院系预聚合；
  - 数据量继续增长时，按时间分区 `posts`、`matches`、`claims`。

### 5.4 索引维护成本

- GIN 三元组索引 2.2 MB，查询收益显著，适合读多写少的帖子表；
- 部分索引体积小，但写路径仍需维护；没有查询收益时应谨慎保留；
- 基准脚本会临时删除并重建索引，只允许在 `clfp_bench` 上运行。

## 6. 复现方式

```bash
# 1. 创建基准库并迁移（在 postgres 下执行）
psql "postgresql://.../postgres" -c "DROP DATABASE IF EXISTS clfp_bench WITH (FORCE);"
psql "postgresql://.../postgres" -c "CREATE DATABASE clfp_bench;"
DATABASE_URL="postgresql://.../clfp_bench" npx prisma migrate deploy
DATABASE_URL="postgresql://.../clfp_bench" npx tsx prisma/seed.ts

# 2. 生成 10 万级数据
DATABASE_URL="postgresql://.../clfp_bench" npx tsx scripts/db/generate-data.ts

# 3. 运行基准
DATABASE_URL="postgresql://.../clfp_bench" npx tsx scripts/db/benchmark.ts
```

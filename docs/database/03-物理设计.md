## 2. 数据类型与存储策略

### 2.1 标识符

- 所有业务表主键使用 `TEXT`，值由 Prisma 的 `cuid()` 在应用层生成，数据库**没有**默认值或序列。
- 直接写 SQL 插入数据时必须显式提供 `id`，否则会因 `NOT NULL` 失败。
- CUID 长度约 25 字符，随机性强但非严格单调；作为聚簇主键时会产生一定的索引页分裂，但当前数据量下可接受。
- 外键列同为 `TEXT`，与主键类型一致，避免隐式转换导致索引失效。
- `_prisma_migrations.id` 是 `VARCHAR(36)`，属于 Prisma 内部表。

### 2.2 时间类型

- Prisma 的 `DateTime` 映射为 `TIMESTAMP(3) WITHOUT TIME ZONE`，精度毫秒。
- 应用层统一写入 UTC 时间；数据库不保存时区信息，因此所有直接 SQL 写入也必须使用 UTC，否则会与 Prisma 数据混用。
- 展示层按 `Asia/Shanghai` 格式化；`created_at`、`updated_at`、`occurred_at`、`escalate_at`、`deliver_at` 都遵循同一约定。
- `updated_at` 由 Prisma 在 UPDATE 时自动写入，数据库**没有** `ON UPDATE` 触发器；直接 SQL 更新需要手动赋值。P2 不打算加 `updated_at` 触发器，避免与 Prisma 双写冲突。

### 2.3 文本类型

- 业务文本列统一使用 `TEXT`，没有 `VARCHAR(n)` 长度限制；长度校验在应用层 zod 中完成。
- 优点：避免因业务规则变化改表；缺点：数据库无法阻止超长写入。
- 若课程要求“数据库层也要限制”，P2 可为关键列补 `CHECK (char_length(title) BETWEEN 1 AND 120)` 等约束，作为演示；当前未加。

### 2.4 JSONB

- `matches.detail`、`audit_logs.detail`、`app_configs.value` 使用 JSONB。
- JSONB 支持 GIN 索引与路径查询；当前没有建 JSONB 索引，因为查询主要按主键取整条记录，不按内部字段过滤。
- 如果 P6 需要按 `app_configs.value->>'provider'` 查询，可加表达式索引。

### 2.5 数组与向量

- `post_embeddings.vector` 为 `DOUBLE PRECISION[]`，维度由 `dim` 声明。
- 当前相似度计算在 Node.js 中完成，数据库只负责存储与读取。
- 本机没有 `pgvector` 扩展，因此不采用 `vector` 类型与 HNSW/IVFFlat 索引；这是环境限制，不是设计偏好。报告会把 pgvector 列为未来工作。
- P2 已加 `CHECK (dim = array_length(vector, 1))`，保证声明维度与数组长度一致。

### 2.6 大字段与 TOAST

- `TEXT`、`JSONB`、数组超过约 2 KB 时，PostgreSQL 会自动使用 TOAST 存储，主表行只保留指针。
- 图片二进制不进入数据库，避免大对象（BLOB）导致备份膨胀与 VACUUM 压力；数据库只保存 `post_images.path`、`mime_type`、`size`。

### 3.1 P1 基线的索引问题（P2 已处理）

1. **trigram 索引缺失**：`posts` 的关键词搜索使用 `ILIKE '%关键词%'`，没有 GIN trigram 索引时只能顺序扫描；10 万级数据下会成为瓶颈。
2. **公开信息流没有部分索引**：`posts_status_deleted_at_created_at_idx` 以 `status` 开头，而公开列表主要按 `deleted_at IS NULL AND taken_down_at IS NULL AND archived_at IS NULL` 过滤，再按 `created_at` 排序；现有索引不能很好覆盖这种组合。
3. **待审认领扫描没有部分索引**：`claims_status_escalate_at_idx` 包含所有状态；超时转交只关心 `status = 'PENDING' AND escalated_at IS NULL`。
4. **未读通知没有部分索引**：`notifications_user_id_read_at_idx` 包含已读与未读；未读角标只查 `read_at IS NULL`。
5. **统计类查询缺少时间索引**：`matches.created_at`、`claims.created_at`、`users.created_at` 没有单独索引，统计按时间范围聚合时可能全表扫描。
6. **`post_images` 的排序没有唯一约束**：同一帖子可能出现重复 `sort_order`，配图顺序不稳定。

P2 已通过 `01_constraints_indexes.sql` 与迁移 `20261102090000_db_course_constraints_indexes` 逐个处理上述问题：重建三个 trigram 索引，新增公开信息流与待审认领的部分索引、未读通知部分索引、统计时间索引，并给 `post_images(post_id, sort_order)` 加唯一索引。P6 会用 10 万级数据比较“有索引/无索引”的执行计划与耗时。

### 3.2 P2 已建立索引（P6 验证）

以下索引先写入 P2 迁移，P6 用 10 万级数据做 `EXPLAIN (ANALYZE, BUFFERS)` 对比；如果实测无收益，会在报告中说明并移除。

| 索引名 | 表 | 定义 | 目的 |
| --- | --- | --- | --- |
| `posts_public_feed_idx` | `posts` | `(type, created_at DESC) WHERE deleted_at IS NULL AND taken_down_at IS NULL AND archived_at IS NULL` | 公开信息流按类型 + 时间 |
| `posts_public_category_idx` | `posts` | `(category_id, created_at DESC) WHERE deleted_at IS NULL AND taken_down_at IS NULL AND archived_at IS NULL` | 公开信息流按类别 |
| `posts_title_trgm_idx` | `posts` | `GIN (title gin_trgm_ops)` | 中文关键词模糊检索 |
| `posts_description_trgm_idx` | `posts` | `GIN (description gin_trgm_ops)` | 描述检索 |
| `posts_location_trgm_idx` | `posts` | `GIN (location gin_trgm_ops)` | 地点检索 |
| `claims_pending_escalate_idx` | `claims` | `(escalate_at) WHERE status = 'PENDING' AND escalated_at IS NULL` | 超时转交批量扫描 |
| `claims_one_accepted_per_post` | `claims` | `UNIQUE (post_id) WHERE status = 'ACCEPTED'` | 一条帖子最多一条通过 |
| `notifications_unread_idx` | `notifications` | `(user_id) WHERE read_at IS NULL AND deliver_at <= now()` | 未读角标 |
| `matches_created_at_idx` | `matches` | `(created_at)` | 统计匹配量 |
| `claims_created_at_idx` | `claims` | `(created_at)` | 统计认领量 |
| `users_department_idx` | `users` | `(department) WHERE role = 'USER'` | 按院系统计 |
| `post_images_post_sort_key` | `post_images` | `UNIQUE (post_id, sort_order)` | 配图顺序唯一 |

> 部分索引的谓词不能引用 `now()`，因为 `now()` 不是 immutable；因此未读通知索引若需要“已送达”条件，应写成 `WHERE read_at IS NULL`，送达时间在查询时过滤。上表中的 `deliver_at <= now()` 仅表示查询条件，不进入索引谓词。

## 4. 软删除与可见性

`posts` 用三个时间戳表达不同可见性：

| 字段 | 语义 | 公开列表 | 作者 | 管理员 | 可恢复 |
| --- | --- | --- | --- | --- | --- |
| `deleted_at` | 删除 | 不可见 | 不可见（除非另行处理） | 可见 | 作者不可恢复 |
| `taken_down_at` | 下架 | 不可见 | 可见 | 可见 | 可恢复 |
| `archived_at` | 归档 | 不可见 | 可见 | 可见 | 可取消归档 |

物理设计上：

- 所有公开查询都要带三个 `IS NULL` 条件，容易漏写；P2 用 `v_public_posts` 视图统一封装，应用层优先从视图读取；
- 部分索引的谓词与视图条件保持一致，保证查询能命中索引；
- 统计口径需要区分“发布量（排除删除）”“已下架”“已归档”，不能简单用 `deleted_at IS NULL` 一刀切。

## 5. 安全存储设计

| 数据 | 存储方式 | 数据库可见性 | 说明 |
| --- | --- | --- | --- |
| 登录密码 | `password_hash`，scrypt 加盐哈希 | 只存哈希 | 不可逆；数据库泄露不能直接还原密码 |
| 会话令牌 | `token_hash`，SHA-256 摘要 | 只存摘要 | 原始令牌只在 Cookie 中，库里没有可用令牌 |
| 手机号 | `phone_encrypted`（AES-256-GCM）+ `phone_masked` | 密文 + 脱敏值 | 密钥在 `ENCRYPTION_KEY` 环境变量，换钥会导致旧密文无法解密 |
| 认领联系方式 | `contact_encrypted` + `contact_masked` | 密文 + 脱敏值 | 只有双方互相授权后，应用层才解密完整值 |
| 认证信息 | 不存储 | — | 无 |

物理设计含义：

- 加密字段无法做 `LIKE` 或等值检索；业务也不需要按手机号搜索，因此可接受；
- 备份文件包含密文，但不包含密钥；密钥必须单独备份；
- 当前应用使用单一数据库账号，数据库层无法区分“谁能看密文”。P4 会建角色并演示列级授权与 RLS；生产环境应让应用账号只能通过受控视图访问敏感列。

## 6. 文件存储与数据库的边界

- 帖子配图存放在项目目录 `storage/uploads/`，`post_images.path` 保存相对路径，`mime_type` 与 `size` 保存元数据。
- 数据库与文件系统没有事务一致性：插入图片记录成功但文件写入失败，或文件写入成功但事务回滚，都会产生不一致。
- 现有应用通过“先写文件、再写数据库、失败时清理”降低风险；P7 备份时必须同时备份数据库与 `storage/uploads/`。
- 不把图片存成 `BYTEA` 的原因：备份体积、WAL 膨胀、VACUUM 成本、读取放大；改用对象存储时只需改 `src/lib/storage.ts`，数据库结构不变。

## 7. 扩展、增长与分区

- 当前数据量：种子只有 2 个账号，实际演示数据由 E2E 临时创建并清理；P6 会在独立 `clfp_bench` 库生成 10 万级数据。
- 预计增长最快的是 `notifications` 与 `audit_logs`，其次是 `matches` 与 `claims`。
- 当前未分区。若数据量继续增长，可按月对 `notifications`、`audit_logs` 做范围分区（`PARTITION BY RANGE (created_at)`），历史分区可归档或只读；这属于 P6 之后的可选优化，不在本期必做范围。
- `pg_trgm` 的 GIN 索引写入成本较高，适合读多写少的帖子表；P6 会用实际数据比较“有索引/无索引”的插入与查询成本。
- 自动清理（autovacuum）使用默认配置；大量软删除与更新会让 `posts` 产生死元组，P6 可观察 `pg_stat_user_tables` 的 `n_dead_tup` 并调整参数。

## 8. 当前权限与备份概况

- 开发环境应用使用 `clfp` 账号，拥有数据库 DDL/DML 权限；没有为应用、统计、只读分别建角色。
- 数据库备份使用 `pg_dump -Fc`，客户端工具在 `D:\Program Files\PostgreSQL\18\bin`；P7 会补恢复验证脚本。
- 当前没有配置 WAL 归档与 PITR；P7 只在文档中说明原理与生产建议，不在本机搭建完整 PITR。

## 9. 物理设计结论

- 存储结构以 heap + B-tree 为主，JSONB/数组用于半结构化与向量属性，图片外置；
- 现有索引覆盖了主键、唯一性与大部分外键查询，但公开信息流、超时扫描、未读通知、关键词搜索缺少针对性索引；
- P2 已补齐公开信息流、待审认领、未读通知、关键词检索与统计所需索引；分区仍不在本期范围，P4 会补角色与 RLS 演示，P6 评估分区与大数据量表现；
- 最大的物理层风险原本是**搜索索引缺失**与**统计数据量增长后的全表聚合**：前者已由 P2 的 trigram 索引解决，后者已由 P3 的 SQL 统计函数解决，P6 用实测数据验证。

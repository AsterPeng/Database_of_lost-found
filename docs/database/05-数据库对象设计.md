# 05 数据库对象设计

本文档是 P2 的实现清单。所有对象通过手写 SQL 放入新的 Prisma 迁移，由 `prisma migrate` 统一执行；不在数据库里手工创建，避免迁移历史与真实结构漂移。

## 1. 设计原则

1. **Prisma 继续负责常规 CRUD**：视图、函数、触发器、部分索引、物化视图等 Prisma schema 无法表达的对象，全部写入手写迁移。
2. **函数默认 `SECURITY INVOKER`**：调用者权限决定能做什么，避免无意中创建高权限入口；只有明确需要跨权限读取的只读视图才考虑 `SECURITY DEFINER`，并固定 `search_path`。
3. **业务失败用返回值表达，约束失败用异常表达**：`fn_review_claim` 等函数返回 `jsonb`（`ok`、`code`、`message`），便于应用层映射；触发器违反完整性时 `RAISE EXCEPTION`，让事务回滚。
4. **锁顺序一致**：认领审核按 `claims → posts → handovers` 的顺序加锁，降低死锁概率。
5. **通知仍由应用层生成**：P2 不把通知文案下沉到触发器，避免与现有 241 项 E2E 的文案、免打扰逻辑冲突；触发器只负责审计与完整性。
6. **可重复执行**：迁移内使用 `CREATE OR REPLACE`、`DROP ... IF EXISTS`、`IF NOT EXISTS`，保证在全新库与现有库上都能应用。

## 2. 视图

### 2.1 `v_public_posts` 公开帖子视图

**目的**：把“公开可见”的过滤条件集中到一处，避免应用层漏写 `deleted_at/taken_down_at/archived_at`。

**定义要点**：

```sql
CREATE OR REPLACE VIEW v_public_posts AS
SELECT
  p.id, p.author_id, p.type, p.title, p.description,
  p.category_id, c.name AS category_name,
  p.location, p.occurred_at, p.status, p.resolved_at,
  p.created_at, p.updated_at,
  u.nickname AS author_nickname,
  u.department AS author_department,
  cover.id AS cover_image_id,
  COALESCE(img.image_count, 0) AS image_count
FROM posts p
JOIN users u ON u.id = p.author_id
JOIN categories c ON c.id = p.category_id
LEFT JOIN LATERAL (
  SELECT pi.id
  FROM post_images pi
  WHERE pi.post_id = p.id
  ORDER BY pi.sort_order ASC
  LIMIT 1
) cover ON true
LEFT JOIN LATERAL (
  SELECT COUNT(*)::int AS image_count
  FROM post_images pi
  WHERE pi.post_id = p.id
) img ON true
WHERE p.deleted_at IS NULL
  AND p.taken_down_at IS NULL
  AND p.archived_at IS NULL;
```

**使用方**：P3 之后可用于公开信息流、搜索候选、详情页的只读查询；当前应用仍主要使用 Prisma，视图先用于演示 SQL 与统计。

### 2.2 `v_claim_detail` 认领详情视图

**目的**：把认领、帖子、申请人、审核人、交接状态拼成一行，方便管理员与当事人页面查询。

**主要列**：`claim_id`、`post_id`、`post_title`、`post_author_id`、`claimant_id`、`claimant_nickname`、`status`、`reviewed_by_id`、`reviewer_role`、`escalate_at`、`escalated_at`、`meet_at`、`meet_place`、`handover_completed_at`、`grant_count`。

**注意**：联系方式密文与脱敏值可以出现在视图中，但视图不负责解密；应用层仍按授权判断后再解密。

### 2.3 `v_match_overview` 匹配总览视图

**目的**：匹配页与管理统计使用，一次取出双方帖子摘要、作者、分数与反馈。

**主要列**：`match_id`、`score`、`feedback`、`created_at`、`lost_post_id`、`lost_title`、`lost_author_id`、`lost_author_nickname`、`found_post_id`、`found_title`、`found_author_id`、`found_author_nickname`。

### 2.4 `v_admin_dashboard` 管理首页汇总视图

**目的**：管理后台首页的“用户数、信息数、匹配数、待处理认领、已下架、24 小时新增、找回率”一次查询完成。

**实现**：用 `SELECT ...` 子查询或 CTE 汇总；P3 可替换 `src/app/admin/page.tsx` 中的多次 `prisma.count`。

### 2.5 `v_pending_claims` 待处理认领视图

**目的**：管理员待办与超时扫描。

**过滤**：`status = 'PENDING'`，包含 `escalated_at` 是否为空、等待时长。

### 2.6 `v_unread_notifications` 未读通知视图

**目的**：导航角标与通知中心未读列表。

**过滤**：`read_at IS NULL AND deliver_at <= now()`；`now()` 在视图查询时求值，不进入索引谓词。

## 3. 物化视图

### 3.1 `mv_stats_department` 院系统计物化视图

**列**：`department`、`users`、`posts`、`resolved`、`recovery_rate`。

**定义要点**：

```sql
CREATE MATERIALIZED VIEW mv_stats_department AS
WITH user_counts AS (
  SELECT COALESCE(department, '未填写') AS department, COUNT(*)::int AS users
  FROM users
  WHERE role = 'USER' AND status = 'ACTIVE'
  GROUP BY 1
),
post_counts AS (
  SELECT COALESCE(u.department, '未填写') AS department,
         COUNT(*)::int AS posts,
         COUNT(*) FILTER (WHERE p.status = 'RESOLVED')::int AS resolved
  FROM posts p
  JOIN users u ON u.id = p.author_id
  WHERE p.deleted_at IS NULL
  GROUP BY 1
)
SELECT
  COALESCE(uc.department, pc.department) AS department,
  COALESCE(uc.users, 0) AS users,
  COALESCE(pc.posts, 0) AS posts,
  COALESCE(pc.resolved, 0) AS resolved,
  CASE WHEN COALESCE(pc.posts, 0) = 0 THEN 0
       ELSE ROUND(COALESCE(pc.resolved, 0)::numeric / pc.posts * 100)::int
  END AS recovery_rate
FROM user_counts uc
FULL JOIN post_counts pc ON pc.department = uc.department;

CREATE UNIQUE INDEX mv_stats_department_key ON mv_stats_department (department);
```

**刷新**：`fn_refresh_stats_mv()` 执行 `REFRESH MATERIALIZED VIEW mv_stats_department` 与 `mv_stats_category`。P3 在统计页提供“刷新统计快照”按钮，或由 P6 脚本定时刷新。物化视图用于“全部时间总览”，带时间筛选的实时报表仍走 `fn_stats`，避免数据陈旧影响口径。

### 3.2 `mv_stats_category` 类别统计物化视图

**列**：`category`、`posts`、`resolved`、`recovery_rate`。定义同理，按 `categories.name` 聚合未删除帖子。

## 4. 函数与存储过程

### 4.1 `fn_review_claim` 认领审核

**签名**：

```sql
CREATE OR REPLACE FUNCTION fn_review_claim(
  p_claim_id text,
  p_reviewer_id text,
  p_decision text,
  p_note text DEFAULT NULL
) RETURNS jsonb
LANGUAGE plpgsql
AS $$ ... $$;
```

**输入**：

| 参数 | 说明 |
| --- | --- |
| `p_claim_id` | 认领 ID |
| `p_reviewer_id` | 审核人用户 ID |
| `p_decision` | `ACCEPT` 或 `REJECT` |
| `p_note` | 审核备注，可空 |

**返回**（示例）：

```json
{
  "ok": true,
  "status": "ACCEPTED",
  "reviewerRole": "OWNER",
  "claimantId": "c...",
  "postId": "p...",
  "postTitle": "丢失一把钥匙",
  "rejectedClaimantIds": ["c...", "c..."]
}
```

**处理步骤**：

1. `SELECT * FROM claims WHERE id = p_claim_id FOR UPDATE`，锁定认领；
2. 校验认领存在且状态为 `PENDING`；
3. `SELECT * FROM posts WHERE id = claim.post_id FOR UPDATE`，锁定帖子；
4. 查询审核人，判断权限：
   - 审核人是帖子作者 → `reviewerRole = 'OWNER'`；
   - 审核人是管理员且认领已转交（`escalated_at IS NOT NULL`）→ `reviewerRole = 'ADMIN'`；
   - 否则返回 `{ok:false, code:'FORBIDDEN'}`；
5. `REJECT`：
   - `UPDATE claims SET status='REJECTED', review_note, reviewed_by_id, reviewed_at, reviewer_role`；
   - 返回被拒认领信息；
6. `ACCEPT`：
   - 校验帖子仍为 `OPEN`、未删除、未下架；
   - `UPDATE posts SET status='RESOLVED', resolved_at=now()`，条件带 `status='OPEN'`；
   - `UPDATE claims SET status='ACCEPTED', ...`；
   - `UPDATE claims SET status='REJECTED', review_note='该物品已被其他申请人认领', ... WHERE post_id=... AND id<>... AND status='PENDING'`；
   - `INSERT INTO handovers(claim_id) VALUES (p_claim_id) ON CONFLICT (claim_id) DO NOTHING`；
   - 返回接受的认领与自动拒绝的申请人列表；
7. 所有步骤在同一事务内，由调用方（Server Action）控制提交/回滚。

**并发正确性**：`FOR UPDATE` 锁认领与帖子；即使 10 个请求同时审核同一帖子，只有一个能把帖子从 `OPEN` 改为 `RESOLVED`，其余返回 `POST_NOT_OPEN` 或 `CLAIM_NOT_PENDING`。P5 会用 10 并发验证。

**审计**：管理员审核的审计日志由 `trg_claim_audit` 触发器写入，函数本身不重复写。

### 4.2 `fn_escalate_overdue_claims` 超时转交

**签名**：

```sql
CREATE OR REPLACE FUNCTION fn_escalate_overdue_claims()
RETURNS jsonb
LANGUAGE plpgsql
AS $$ ... $$;
```

**行为**：

- 使用 `FOR rec IN SELECT ... WHERE status='PENDING' AND escalated_at IS NULL AND escalate_at <= now() FOR UPDATE SKIP LOCKED LOOP` 批量锁定；
- 逐条 `UPDATE claims SET escalated_at = now()`；
- 收集 `claim_id`、`post_id`、`post_title`、`claimant_id`；
- 返回 `{ "count": n, "claims": [ ... ] }`；
- 应用层根据返回结果通知管理员，保持现有通知文案与免打扰逻辑。

`SKIP LOCKED` 避免多个页面/进程同时扫描时互相阻塞；游标循环用于演示 PL/pgSQL 的批量处理。

### 4.3 `fn_complete_handover` 确认交接完成

**签名**：

```sql
CREATE OR REPLACE FUNCTION fn_complete_handover(
  p_claim_id text,
  p_user_id text
) RETURNS jsonb
LANGUAGE plpgsql
AS $$ ... $$;
```

**行为**：

- 锁定认领，校验状态为 `ACCEPTED`；
- 校验 `p_user_id` 是申请人或帖子作者；
- `INSERT INTO handovers(claim_id, completed_at, completed_by_id) VALUES (...) ON CONFLICT (claim_id) DO UPDATE SET completed_at = COALESCE(handovers.completed_at, now()), completed_by_id = COALESCE(handovers.completed_by_id, p_user_id)`；
- 返回 `{ok, completedAt, completedById}`；
- 幂等：重复调用不会覆盖第一次完成时间。

### 4.4 `fn_stats` 统计下推

**签名**：

```sql
CREATE OR REPLACE FUNCTION fn_stats(
  p_since timestamp,
  p_until timestamp,
  p_department text DEFAULT NULL
) RETURNS jsonb
LANGUAGE sql
STABLE
AS $$ ... $$;
```

**返回结构**：

```json
{
  "totals": {
    "users": 0,
    "newUsers": 0,
    "posts": 0,
    "resolved": 0,
    "matches": 0,
    "claims": 0,
    "takenDown": 0
  },
  "recoveryRate": 0,
  "byDepartment": [
    {"department": "计算机科学与技术学院", "users": 0, "posts": 0, "resolved": 0, "recoveryRate": 0}
  ],
  "byCategory": [
    {"category": "证件", "posts": 0, "resolved": 0}
  ],
  "departments": ["计算机科学与技术学院"]
}
```

**口径**（必须与 `src/lib/stats.ts` 的现有实现逐项一致）：

- `users`：`role='USER' AND status='ACTIVE'`，不受时间范围影响；
- `newUsers`：`role='USER' AND created_at` 在范围内，不按状态过滤；
- `posts`：`deleted_at IS NULL AND created_at` 在范围内，下架与归档仍计入；
- `resolved`：上述帖子中 `status='RESOLVED'`；
- `takenDown`：上述帖子中 `taken_down_at IS NOT NULL`；
- `matches`：`created_at` 在范围内，且双方帖子都未删除；
- `claims`：`created_at` 在范围内，且关联帖子未删除；
- 院系筛选：用户按 `department`，帖子按作者院系，匹配按任一方院系，认领按帖子作者或申请人院系；
- `byDepartment`：用户按 `COALESCE(department,'未填写')`，帖子按作者院系，包含只出现用户或只出现帖子的院系；
- `byCategory`：按类别名称聚合未删除帖子；
- `recoveryRate`：`ROUND(resolved / posts * 100)`，`posts=0` 时为 0；
- `departments`：`role='USER'` 且 `department IS NOT NULL` 的去重列表。

**实现要点**：用多个 CTE 分别算用户、帖子、匹配、认领，再 `jsonb_build_object` 组装；排序在 SQL 中按 `posts DESC, users DESC, department`，如果与 JS 的 `zh-CN` 排序在个别院系上不一致，P3 的对比测试会暴露，应用层保留最终排序作为兜底。

**为什么用 `STABLE`**：函数只读，允许 PostgreSQL 在单条语句内复用快照；不修改数据。

## 5. 触发器

### 5.1 `trg_post_status_transition`

- **时机**：`BEFORE UPDATE OF status ON posts`
- **规则**：
  - `OPEN → RESOLVED` 允许；
  - `OPEN → CLOSED` 允许；
  - 其他状态变化（`RESOLVED/CLOSED → OPEN`、`RESOLVED → CLOSED` 等）拒绝；
- **异常**：`RAISE EXCEPTION 'invalid post status transition: % -> %'`；
- **兼容性检查**：实施前先确认应用没有合法的“重新打开”路径；如果有，P2 调整规则并在文档记录。

### 5.2 `trg_match_integrity`

- **时机**：`BEFORE INSERT OR UPDATE ON matches`
- **规则**：
  - `lost_post_id <> found_post_id`；
  - `lost_post_id` 对应帖子 `type='LOST'`；
  - `found_post_id` 对应帖子 `type='FOUND'`；
  - 两位作者不同；
- **异常**：`RAISE EXCEPTION`，事务回滚；
- **注意**：验重逻辑用 `SELECT ... FOR SHARE` 读取帖子，避免与帖子类型更新竞争；帖子类型实际不允许修改，风险低。

### 5.3 `trg_claim_audit`

- **时机**：`AFTER UPDATE OF status ON claims`
- **条件**：`OLD.status = 'PENDING' AND NEW.status IN ('ACCEPTED','REJECTED') AND NEW.reviewer_role = 'ADMIN'`
- **动作**：向 `audit_logs` 插入 `action='CLAIM_REVIEW'`、`target_type='CLAIM'`、`target_id=NEW.id`，`detail` 包含帖子标题、决定、备注；
- **去重**：P3 移除 `src/server/claim-actions.ts` 中管理员审核的手写审计插入，改由触发器负责；
- **为什么只对管理员**：作者审核属于业务操作，不进入管理操作日志；这与现有应用逻辑一致。

### 5.4 可选 `trg_claim_result_notification`

- **时机**：`AFTER UPDATE OF status ON claims`
- **动作**：向 `notifications` 插入审核结果通知；
- **暂不启用**：通知文案、免打扰、收件人（通过/拒绝、同帖其他申请人）逻辑较复杂，P2 先保持应用层生成，待 P3 对比测试通过后再评估是否下沉。

## 6. 约束与索引

完整清单见 02 文档 6.3 与 03 文档 3.2。实现顺序：

1. 先补可空外键（`claims.match_id`、`handovers` 两个用户外键），执行前做数据校验；
2. 再补 CHECK 约束（分数、免打扰小时、公告过期、配图大小、向量维度、多态类型、审核角色）；
3. 再加唯一约束/部分唯一索引（`post_images(post_id, sort_order)`、`claims_one_accepted_per_post`）；
4. 最后加性能索引（公开信息流、trgm、待审认领、未读通知、统计时间列）；
5. 索引创建后执行 `ANALYZE`，让统计信息生效。

**注意**：`CREATE INDEX CONCURRENTLY` 不能在 Prisma 迁移的事务中执行；P2 使用普通 `CREATE INDEX`，在开发库与演示库上可接受。生产环境应单独用并发创建。

## 8. 错误码约定

函数返回的 `code` 使用大写蛇形：

| code | 含义 |
| --- | --- |
| `CLAIM_NOT_FOUND` | 认领不存在 |
| `CLAIM_NOT_PENDING` | 认领已被处理 |
| `FORBIDDEN` | 审核人无权限 |
| `INVALID_DECISION` | 决定不是 `ACCEPT`/`REJECT` |
| `POST_NOT_OPEN` | 帖子已结束、删除或下架 |
| `HANDOVER_NOT_ALLOWED` | 交接不是通过状态或用户不是当事人 |

应用层把这些 code 映射为现有页面的静默返回或错误提示，保持 E2E 行为不变。

## 9. 验收与回滚

**验收**：

- 在全新数据库执行 `prisma migrate deploy`，所有对象创建成功；
- 在现有 `clfp_dev` 执行迁移，数据不丢失，`prisma migrate status` 干净；
- `npm run verify:m1`、`verify:e2e`、`verify:admin-claims`、`verify:stats` 全部通过；
- SQL 冒烟测试覆盖：视图可查、函数正常/异常分支、触发器拒绝非法状态、部分唯一索引阻止第二条 `ACCEPTED`；
- P5 并发测试恰好一条通过。

**回滚**：

- Prisma 迁移只前进不回滚；每个迁移对应一个手写 `db/sql/rollback_XX.sql`，在需要时由人工在事务中执行；
- 回滚顺序与创建顺序相反：先删触发器/函数/视图/物化视图，再删索引/约束/外键；
- 回滚前先做 `pg_dump` 备份，禁止在未备份的库上直接回滚。

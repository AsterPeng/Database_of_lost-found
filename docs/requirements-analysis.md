## 0. 首先要说清楚的一件事：文档要求的是「微信小程序」，不是网页

需求文档标题写明**「微信小程序」**，并且三条需求使用了只有小程序才能实现的能力：

| 需求 | 依赖的小程序专属能力 | 网页能否实现 |
| --- | --- | --- |
| CLFP-USR-0001 微信授权登录，以 openid 为唯一标识 | `wx.login` + `code2session` | ❌ 网页拿不到微信 openid |
| CLFP-USR-0002 打开即静默登录，无需账号密码 | 小程序免登录态 | ⚠️ 网页只能做扫码登录，体验不同 |
| CLFP-USR-0013 小程序订阅消息推送 | 微信订阅消息 | ❌ 网页无法推送微信服务通知 |

这与此前会话中确认的「Next.js 网页」方案冲突。因此有一个方向必须先定：

- **方向 A（按文档）**：做微信小程序，另配一个**网页管理后台**给管理员用。学生端是小程序，管理员端是网页。
- **方向 B（一套代码两处运行）**：用 Taro 写一套代码，同时编译出**微信小程序 + H5 网页**，另配管理后台。**推荐**，既满足文档，又保留「网页」形态，演示和答辩时也方便。
- **方向 C（只做网页）**：放弃 openid 登录和订阅消息，用手机号+验证码或邮箱登录。与文档不符，需要改需求。

后文均按**方向 B**展开。

## 1. 需求逐条解读：怎么做、风险在哪

### 1.1 账号与身份（0001、0002、0021）

- 0001 / 0002 可实现：`wx.login` 拿 code → 后端 `code2session` 换 openid/session_key → 以 openid 建号。首次进入引导填写姓名、学号或工号、院系、手机号。
- **风险点 1**：需求说「用于校内身份核验」，但**学校不会自动告诉你这个人是不是本校学生**。三种做法：
  - 对接学校统一身份认证 / 教务系统（需要学校提供接口与授权，通常周期很长）；
  - 学号规则弱校验（如学号位数、入学年份）+ 人工抽检；
  - 管理员人工审核。
  需要你说明学校是否能给接口，否则只能按第 2/3 种做，并明确告知用户「未强制核验」。
- **风险点 2**：手机号获取（`getPhoneNumber`）**要求小程序为非个人主体并已认证**，个人主体小程序拿不到。
- 0021 毕业/离职后自动归档：需要学籍状态数据源。若拿不到，只能退化为「管理员手动归档 + 按学号入学年份到期自动归档」。

### 1.2 发布与信息流（0003 ~ 0007、0023）

- 0003 / 0004：发布寻物、拾物，1~6 张照片。图片先压缩再上传，服务端存对象存储或本地磁盘。
- 0005：仅「未完成」可编辑/删除，已完成或已认领只读 —— 需要在服务端校验，不能只靠前端隐藏按钮。
- 0006：类别固定为卡证、电子设备、钥匙、书籍、服饰、其它，加上时间范围、地点范围筛选。类别需可配置（见 0025）。
- 0007：关键词搜索（名称/描述/地点）+ 相关度排序，返回失物与拾物两类结果。**这与 0008 的语义匹配是两套东西**：0007 是关键词检索，0008 是向量语义匹配，要分别实现并在界面上区分。
- 0023：失主收到归还后可标记「已找回」，状态变为已完成。需要一个明确的状态机（寻找中 / 已匹配 / 认领中 / 已完成 / 已关闭）。

### 1.3 RAG 匹配（0008 ~ 0010、0020）

- 0008：把用户发布的物品描述向量化，与历史记录做语义匹配，按置信度**双向**推送（失主看到可能捡到自己东西的拾物帖，反之亦然）。**这是整个项目的核心，也是工作量最大的部分。**
- 0009：「我的匹配」页面，展示对方信息摘要、置信度、推荐时间、类别。
- 0010：反馈「是我的 / 不是我的 / 待核实」，并「据此优化后续推荐模型」。
  - **需要澄清**：真正的在线训练模型在小项目里不现实（需要标注数据、训练流程、上线评估）。可落地的做法是**反馈驱动的排序自适应**：把反馈写入权重调整（例如某类别正反馈多则提高该类别权重、调整置信度阈值、屏蔽已判定「不是我的」的配对）。若你确实要求「训练模型」，需要另立训练数据与离线评估方案，工作量翻倍。
- 0020：发布后 5 秒内完成向量化、入库、相似检索；高峰期平均匹配响应 ≤ 2 秒。
  - 5 秒内完成**可行**：入库后写一条任务记录，后台 worker 异步向量化 + 检索 + 生成匹配。避免同步阻塞发布接口。
  - **≤2 秒这条要拆口径**：pgvector 检索本身毫秒级，很容易达标；但如果「匹配响应」包含**调用大模型生成匹配理由**，2 秒就很紧张（大模型首字延迟通常 0.5~2 秒，加上网络抖动）。建议：**检索结果 2 秒内必须返回**，模型生成的解释允许异步补充或只对前 3 条生成。这条验收标准需要你确认口径（答辩时是个容易被问的点）。

### 1.4 认领与交接（0011、0012、0014）

- 0011：发起认领需填写认领凭证（专属特征、购买凭证截图、存放位置），由**对方用户或管理员**审核 —— 两种审核路径都要做，且要能配置默认走哪种。
- 0012：审核通过后双方在线约定线下交接时间与地点，之后点「确认交接完成」，系统记录结果。需要防呆：一方确认后另一方确认才生效，或任一方确认即可（需你定）。
- 0014：联系方式（手机号、微信号）在公共浏览页**默认脱敏**，仅双方达成认领意向并互相授权后可见。这是隐私红线，必须在**服务端接口层**过滤字段，不能靠前端。

### 1.5 通知与消息（0013、0019）

- **这是全项目最大的产品级风险。** 微信订阅消息分两类：
  - **一次性订阅**：用户点一次授权，你只能发一条。任何小程序都能用。
  - **长期订阅**：可多次下发，但**仅对特定行业开放**（政务、医疗、交通等），校园失物招领大概率申请不到。
  - 也就是说：新匹配、认领申请、审核结果、交接提醒这四类推送，实际能做到的是「**用户每次进入小程序时，我们请求他订阅下一批通知**」，无法保证「用户不来小程序也能收到」。这个预期必须提前和指导老师/评审说清楚。
- 0019 消息接收偏好 + 免打扰时段（22:00—次日 7:00）可在服务端实现：定时推送的任务在免打扰时段排队，到点再发。

### 1.6 治理与运营（0015 ~ 0017、0024）

- 0015 举报、0016 管理员审核下架/删除 + 操作日志、0017 统计报表（用户量、发布量、匹配量、认领量、找回率，按院系与时间段导出）。
  - **0016 需要你定审核模式**：先审后发（安全但发布体验差、冷启动慢）还是先发后审（体验好，需配合人工巡检与举报）。建议先发后审 + 敏感词过滤 + 举报入口。
  - 0017 按院系导出，前提是用户资料里有可靠的院系字段（依赖 1.1 的身份核验）。
- 0024 管理员发布公告，首页与登录后首屏展示。实现简单。

### 1.7 非功能（0022、0025）

- 0022：传输全链路 HTTPS（小程序强制要求），身份信息与联系方式加密存储。
  - 「图片加密存储」成本较高，且要权衡：如果密钥在应用里，加密意义有限。建议分层：**密码做哈希、手机号等敏感字段做字段级加密 + 展示脱敏 + 数据库磁盘加密**，图片用私有读取 + 签名 URL。需要你确认严格程度（毕设答辩通常接受这个层次）。
- 0025：**不改业务代码即可新增类别、调整匹配阈值、接入新模型** —— 这条是很好的工程要求，我会用配置表 + 模型适配层来满足：
  - 类别表存数据库，管理后台可增删；
  - 匹配阈值存在配置表，管理后台可调；
  - 向量模型/大模型通过统一接口抽象，配置项切换（这项在之前的 PRD 里已经预留）。

### 1.8 关于表格首列的 `*`

带 `*` 的有 20 条，不带 `*` 的是 **0015 举报、0017 统计报表、0019 消息偏好、0021 归档、0024 公告**这 5 条。我推测 `*` 表示核心/必做。请确认：这 5 条是「可选/加分项」还是同样必做？

## 2. 必须由你提供或决定的外部条件

这些不是写代码能解决的，缺任何一项都会卡住：

| # | 事项 | 为什么必须 |
| --- | --- | --- |
| 1 | **微信小程序 AppID 与主体类型**（个人 / 学校 / 公司） | 决定能否用手机号获取、订阅消息；个人主体功能受限 |
| 2 | 小程序是否已认证、是否已做**小程序备案** | 2024 年起未备案的小程序无法发布 |
| 3 | **服务器 + 已备案域名 + HTTPS 证书** | 小程序 request 合法域名必须 HTTPS 且备案；没有就无法真机联调 |
| 4 | 学校能否提供**统一身份认证/教务接口** | 决定学号院系是自动核验还是人工 |
| 5 | **大模型与向量模型的服务商和 API Key** | 无 Key 时可用降级模式开发，但 0008 无法真实验收 |
| 6 | 图片存储放哪（服务器磁盘 / 对象存储 / 微信云托管） | 影响部署与成本 |
| 7 | 交付时间与用途（毕设？课程作业？真实上线？） | 决定范围裁剪与优先级 |

**开发期的替代方案**：没有 AppID 时可用微信官方「小程序测试号」开发；没有域名时可在微信开发者工具中关闭域名校验做本地联调；没有模型 Key 时用降级检索模式（关键词 + 结构化 + 本地哈希向量），保证流程完整可演示。

## 3. 技术方案

### 3.1 选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 小程序端 | **Taro 4 + React + TypeScript** | 一套代码编译微信小程序与 H5；TS 类型与后端共享 |
| 管理后台（网页） | **Next.js + Ant Design** | 管理员用的网页端，也承载统计报表导出 |
| 后端 API | **Node.js + NestJS（或 Fastify）+ Prisma** | 与前端同语言，类型直通；Prisma 迁移管理清晰 |
| 数据库 | **PostgreSQL 18（本机已装）** | 已具备，无需 Docker；后续可启用 pgvector |
| 向量检索 | 开发期：应用层余弦相似度（向量存 JSONB）；上线：**pgvector** | 本机 PostgreSQL 尚未安装 pgvector，先用应用层实现避免阻塞；数据量到万级再切 |
| 异步任务 | 数据库任务表 + worker 进程（不引入 Redis） | 满足「5 秒内完成向量化」，同时减少部署依赖 |
| 模型接入 | 统一适配层：`EmbeddingProvider` / `ChatProvider` | 满足 CLFP-USR-0025 不改业务代码换模型 |
| 缓存/队列（可选） | Redis | 只在性能优化阶段引入 |

## 1. 方向调整说明：小程序能力如何用网页替代

原需求按小程序编写，以下四条使用了小程序独有能力，Web 版必须换实现。这是与原始需求文档**唯一存在偏差**的地方，答辩与验收时需要口径一致。

| 需求 | 小程序原方案 | Web 版替代方案 | 影响 |
| --- | --- | --- | --- |
| USR-0001 微信授权登录，openid 为唯一标识 | `wx.login` + `code2session` | **邮箱 + 密码注册**，以用户 ID 为唯一标识；注册后补充姓名、学号/工号、院系、手机号 | 失去「微信一键登录」的便利；如需微信扫码登录，必须申请**微信开放平台网站应用**（企业主体 + 审核），个人不可申请 |
| USR-0002 打开即静默登录 | 小程序免登录态 | 持久化会话 Cookie（记住我，默认 30 天），打开网站免登录；被禁用账号立即失效并提示 | 能力等价 |
| USR-0013 小程序订阅消息推送 | 微信订阅消息 | **站内通知中心 + 邮件通知**（可开关） | 触达弱于微信；邮件需要你提供 SMTP 账号，没有 SMTP 时只做站内通知 |

其余 21 条需求不受方向调整影响，可 1:1 落地。

## 2. 目标与范围

### 2.1 目标

1. 学生能低成本发布寻物/拾物信息（含最多 6 张照片）。
2. 用 **RAG 语义匹配**把失主与拾主的帖子自动配对，并按置信度双向推荐。
3. 提供**认领申请 → 凭证审核 → 线下交接 → 确认完成**的完整闭环。
4. 联系方式受控可见，公共页面默认脱敏。
5. 管理员能审核内容、处理举报、发布公告、导出统计报表。

### 2.2 本期不做

- 微信小程序、微信登录、微信订阅消息（已确认改方向）。
- 即时聊天（本期是站内留言 + 认领申请流程）。
- 物品价值鉴定、担保交易、支付。
- 与学校教务系统的深度对接（无接口时按人工核验处理）。
- 真正的模型训练（见 4.3 对 USR-0010 的口径建议）。

## 4. 核心技术方案

### 4.1 技术栈（最终）

| 层 | 选择 | 说明 |
| --- | --- | --- |
| 前端 | **Next.js（App Router）+ TypeScript + Tailwind + shadcn/ui** | 服务端渲染，利于帖子被搜索收录；移动端优先适配 |
| 后端 | Next.js Route Handlers + 独立 worker 进程 | 小项目不引入第二套后端框架，降低部署复杂度 |
| 数据库 | **PostgreSQL 18（本机已装）** + Prisma | 迁移与类型安全 |
| 向量检索 | 开发期应用层余弦相似度（向量存 `float[]`/JSONB）；数据量上万后切 **pgvector** | 本机暂无 pgvector，先用应用层实现，避免阻塞开发 |
| 异步任务 | 数据库任务表 + worker（`npm run worker`） | 满足「发布后 5 秒内完成向量化」，不引入 Redis |
| 模型接入 | `EmbeddingProvider` / `ChatProvider` 接口，配置切换 mock / 火山方舟 / OpenAI / Ollama | 满足 USR-0025 |
| 认证 | Auth.js（邮箱密码），会话落库 | USR-0002 禁用即时失效 |
| 邮件 | Nodemailer（可选，无 SMTP 时优雅降级为仅站内通知） | USR-0013 |

### 4.2 RAG 匹配设计

**流程**

1. 用户发布/编辑帖子 → 接口立即返回成功，同时写入一条 `embedding_task`。
2. worker 取出任务：把「名称 + 类别 + 地点 + 时间 + 特征描述」拼成文本 → 生成向量 → 入库。
3. 生成向量后做一次相似检索：候选集先按结构化条件收敛（类型互补、类别相符、时间窗 ±30 天、地点相近），再算相似度。
4. 综合打分：`置信度 = w1·向量相似度 + w2·类别匹配 + w3·地点匹配 + w4·时间接近度 + w5·关键词重合`，权重与阈值来自配置表（USR-0025）。
5. 置信度超过阈值的配对写入 `matches`，**双向**可见：失主看到「可能捡到你东西的人」，拾主看到「可能丢东西的人」。
6. 通知：按用户通知偏好下发站内通知（P1 加邮件）。
7. 用户反馈「是我的/不是我的/待核实」→ 更新 `matches.feedback`；「不是我的」的配对永久屏蔽，其余反馈用于调整类别权重与阈值。

**防幻觉原则（与 v0.1 一致）**

- 大模型只用于**生成匹配理由**与**辅助排序**，不允许创造帖子。
- 模型输出的帖子 ID 必须存在于本次候选集，否则丢弃。
- 模型调用失败或超时（>3s）时，直接使用规则打分结果，理由由规则模板生成，页面不报错。

**性能（USR-0020）**

- 发布接口：不阻塞，P95 目标 < 300ms。
- 向量化 + 检索：目标 5 秒内完成（worker 实测）。
- 「平均匹配响应 ≤2 秒」：按**检索出结果**口径实现（索引 + 结构化预过滤，毫秒级）。若口径包含大模型生成理由，则改为异步补全或只对前 3 条生成。

### 4.3 USR-0010「优化推荐模型」的口径建议

真正的在线训练需要标注数据与离线训练流程，成本高且效果不可控。建议采用：

- **反馈驱动的权重自适应**：统计各类别的正/负反馈比例，自动微调类别权重与置信度阈值；
- **黑名单式屏蔽**：已判定「不是我的」的配对不再推荐；
- **可解释**：管理后台展示当前权重与阈值，可手动覆盖。

这套方案能回答「系统根据反馈优化了推荐」的质疑，且完全可演示。若要求真实训练模型，需要另立训练数据标注与离线评估阶段（工作量约增加一倍）。

## 7. 权限与隐私规则

1. 联系方式默认脱敏（如 `138****5678`），仅 `contact_grants` 中已授权的关系可见完整值；**过滤在接口层完成**。
2. 未登录：可浏览与搜索，不可发布、认领、发消息。
3. 作者只能操作自己的帖子；`status = resolved/claimed` 时只读（USR-0005）。
4. 管理员所有操作写入 `audit_logs`。
5. 密码哈希存储；手机号字段级加密；日志中禁止打印联系方式原文。
6. 归档用户（0021）的未完成帖子不进入公开信息流与匹配候选。
7. 图片目录不对外列目录，读取走鉴权或签名 URL。
